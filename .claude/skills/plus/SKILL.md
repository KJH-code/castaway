# plus — 강화 모드

> 이 레포에서는 `/plus` 로 부른다(플러그인이 아니라 `kjh-lyj:` 가 안 붙는다 · 에이전트 이름도 그대로). **병합 규칙은 orchestrate 스킬 머리의 '이 레포에서 바꾼 셋' 1 을 따른다** — 메인이 test 통과 · review 에 실패 없음이면 main 에 합치고, 실패 · 의심이 있으면 보고하고 답을 기다린다(아래 '사용자 승인 없이 기본 브랜치에 병합하기'는 그 경우를 말한다).

기본 모드(`orchestrate` 스킬)의 시작 확인·인터뷰·지시서·검수 흔적 정리·보고 규칙을 따르고, 구현과 검증을 한 칸씩 올린다. 먼저 이 플러그인의 `skills/orchestrate/SKILL.md`를 읽는다.

한도는 기본 모드의 약 3배, 최대 모드의 약 3분의 1이다(작업 단위 3개, Pro 기준 약 9–12%, Max 약 2%, 추정).

| | 절약 | 기본 | **강화** | 최대 |
|---|---|---|---|---|
| 구현 | Haiku max (어려운 단위 Sonnet medium) | Sonnet medium (쉬운 단위 Haiku, 까다로운 단위 Opus medium) | **Opus medium** (worktree) | Opus xhigh (worktree) |
| 설계 | 메인 | 필요하면 1개 | **필요하면 1개** | 후보 3개 + 판정 |
| 테스트 | 병합 후 | 병합 후 | **단위마다 + 병합 후** | 단위마다 + 병합 후 |
| 리뷰 | 가벼운 1명 (Sonnet) | 1명 (Opus xhigh) | **2관점 (Opus xhigh)** | 3관점 (Opus xhigh) |
| 반박 검증 | 없음 | 없음 | **`상` 지적만** | 상위 15개 |
| 증명 검증자 | 1명 | 1명 | **2명** | 3명 |
| 실행 방식 | Agent 도구 | Agent 도구 | **Agent 도구** | 동적 워크플로 |

## 워커

모델·노력은 에이전트 파일에 고정돼 있다. 호출할 때 `model`·`effort`를 넘기지 않는다(훅이 막는다). worktree 격리는 호출할 때 `isolation: "worktree"`로 준다(훅은 이것을 막지 않는다).

| 단계 | 에이전트 | model | effort |
|---|---|---|---|
| 정찰 (처음 보는 영역만) | `su-scout` | sonnet | medium |
| 설계 (판단이 필요할 때) | `w-design` | opus | xhigh |
| 구현 | `w-implement-opus` | opus | medium |
| 단위 테스트 | `su-tester` | haiku | xhigh |
| 병합 후 통합 테스트 | `checker-test` | haiku | xhigh |
| 리뷰 ×2 관점 | `su-reviewer` | opus | xhigh |
| 반박 검증 (`상`만) | `su-verifier` | opus | high |
| 데이터 처리 | `w-data` | haiku | max |
| 실험 실행 | `w-experiment` | haiku | max |
| 잡일 | `w-chore` | haiku | medium |
| 증명 작성 | `su-prover` | opus | xhigh |
| 증명 검증 ×2 관점 | `w-proof-verify` | opus | xhigh |

구현이 Opus medium인 이유: 같은 코딩 테스트에서 Opus가 Sonnet보다 나은 점은 경계 조건 처리였고, Opus high는 medium보다 통과가 늘지 않고 비용만 1.4배였다. 코드 수정 평가(FrontierCode 2.0)에서 크게 오르는 것은 high→xhigh(35.9→43.8%)라, xhigh는 최대 모드에 둔다.

하위 세션은 사용자가 지정한 트랙만 기본 모드 「하위 세션」대로 띄운다.

## 0단계 — 준비와 동의

1. 기본 모드의 "시작할 때 확인"과 1단계 인터뷰를 그대로 한다.
2. 예상 사용량을 보여주고 동의를 받는다.
   ```bash
   node .claude/scripts/budget.js --plan <요금제> --preset plus --units <단위 수> [--scouts 0] [--design 1] --remaining <남은 %>
   # 증명: --preset proof --mode plus
   ```
   이 레포는 플러그인이 아니라 `.claude/` 에 풀어 두었다 — 추정기는 `.claude/scripts/budget.js`. 기본값은 정찰 1, 설계 0이다.

## 1단계 — 정찰과 설계 (필요할 때만)

- 처음 보는 영역이 있으면 `su-scout`를 영역마다 병렬로 띄운다. 사실 목록과 짧은 구조 요약을 받는다.
- 설계 판단이 필요하면 `w-design` 1개에게 맡긴다. 설계안과 작업 단위 목록(파일, 목표, 명령으로 확인 가능한 완료 기준, 기준 브랜치)을 사용자에게 보여주고 **승인을 받는다.**
- 설계가 이미 정해진 작업이면 메인이 단위를 나누고 계획을 보여준 뒤 진행한다.

## 2단계 — 구현과 단위 테스트

시작 전에 메인은 커밋 안 한 변경을 커밋하거나, 지시서에 기준 브랜치를 적는다(worktree는 기본 브랜치에서 갈라진다).

단위마다(서로 독립이면 한 메시지에서 병렬로):
1. `w-implement-opus`를 `isolation: "worktree"`로 띄워 구현하고 커밋하게 한다.
2. `su-tester`가 그 단위의 완료 기준을 실행한다.
3. `실패`면 실패 표와 재현 명령을 **같은 구현 워커에게 SendMessage로 이어서** 준다. 최대 2번. 같은 실패가 반복되면 지시서 문제로 보고 멈춘다.
4. `환경 문제`는 수정 루프에 넣지 않는다. 메인이 해결하거나 사용자에게 묻는다.

## 3단계 — 병합과 통합 테스트

통과한 단위를 메인이 작업 브랜치로 합친다(기본 브랜치에는 합치지 않는다). check 스킬 test 모드(`checker-test`)를 돌린다. 실패면 원인 단위의 구현 워커를 이어서 불러 고친다(최대 2번).

## 4단계 — 리뷰와 반박 검증

1. check 스킬 1단계 시작 상태 기록을 한다.
2. `su-reviewer` 2개를 병렬로 띄운다. 관점은 **스펙·완료 기준 일치** / **정확성·경계 조건·회귀·보안**. 리뷰어는 목표·완료 기준·병합된 diff(`git diff <기준 브랜치>...HEAD`)·레포 경로만 받는다. 구현자의 설명은 넘기지 않는다.
3. 메인이 두 목록의 중복을 합친다. 같은 위치·같은 원인만 합치고, 애매하면 합치지 않는다. 내용은 고쳐 쓰지 않는다.
4. **`상` 지적만** 하나씩 `su-verifier`로 반박 검증한다. `성립`만 확정, `미확인`은 따로 표시, `기각`은 근거와 함께 버린다. `중`·`하`는 "검증 안 함"으로 그대로 보고한다.
5. check 스킬 4단계 흔적 정리를 한다.

## 증명 트랙

1. 작성자는 `su-prover`(Opus xhigh). Fable로 쓰고 싶으면 극한 모드로 바꿀지 사용자에게 묻는다.
2. `w-proof-verify` 2개를 병렬로: **논리**(단계마다 따라 나오는가) / **정의·경계·반례**(정의가 바뀌지 않는가, 극한·특수값·차원, 결론을 깨는 입력을 수치로 찾기). 검증자는 증명문만 받는다.
3. 단계마다 합친다: 누구든 반례·계산으로 `틀림` → 틀림, 둘 다 `성립` → 성립, 나머지 → 근거 부족.
4. 틀림·근거 부족 단계 번호와 이유만 작성자에게 주고(이어서 불러도 된다) 다시 쓰게 한다. 검증자는 매 라운드 새로 띄운다. 최대 3라운드.

## 보고

기본 모드 5단계 양식에 아래를 더한다.

```
## 검증
- 단위별 테스트 표, 병합 후 통합 테스트 표 (환경 문제는 따로)
- 성립한 `상` 지적 (그대로), 미확인·기각 수
- 검증 안 한 `중`·`하` 지적 (그대로, "검증 안 함" 표시)
- 리뷰·검증 에이전트가 만들고 지운 파일
## 비용
- 예상(budget.js), 사용자가 /usage 값을 알려줬으면 실제 차이
- 계층에서 벗어난 곳 (inherit)
```

마지막에 묻는다: "고칠까? 고친다면 어느 항목부터?" 사용자 답 전에는 고치지 않는다.

## 하지 말 것

- 기본 모드의 "하지 말 것" 전부.
- 구현 워커를 worktree 격리 없이 병렬로 띄우기.
- 병합 전 diff만 리뷰하고 끝내기.
- 반박 검증을 거치지 않은 지적을 확정된 문제로 보고하기.
- `환경 문제`를 구현자 수정 루프에 넣기.
- 증명 검증자에게 작성자의 설명이나 다른 검증자 결과 넘기기.
- 이 모드에서 Fable 쓰기 (극한 모드 전용).
