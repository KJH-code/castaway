# start — 읽기 → 인터뷰 → 계획 → 승인 → 모드 → 실행

> 이 레포(CASTAWAY)에서는: CLAUDE.md 가 크다 — '파일 지도' · '계통별 노트' 표로 볼 데를 고르고, 노트(`docs/notes/*.md` — 큰 것 40 KB)는 통째로 읽지 말고 `grep` 으로 대목만 읽는다. `engine/js/data-*.js` · `docs/CASTAWAY_전사_*.md` 는 읽지 않는다.

## 지식은 두 군데에 있다

- **레포 노트** (`docs/notes/`, 팀 공용): 결정, 버그 원인, 실패한 접근·함정. git으로 팀원 모두가 본다. `/reflect`가 쓴다.
  - 위치는 CLAUDE.md에 `notes: <경로>` 줄이 있으면 그 경로를 쓴다. 없으면 `docs/notes/`.
- **Claude Code auto memory** (개인, 이 컴퓨터에만): 사용자 개인 습관·취향. Claude Code가 세션 시작 때 자동으로 읽는다. 이 스킬이 따로 읽을 필요는 없다. 다른 컴퓨터·클라우드 세션·팀원에게는 보이지 않는다.

## 1. 읽기 — 이 단계에서 쓰기 금지

레포에 아무것도 만들거나 고치지 않는다. 빈 노트·빈 폴더·CLAUDE.md 생성 금지.

순서:

1. `CLAUDE.md`, `README*`, `git log --oneline -10`, 현재 브랜치와 `git status --short`
2. 레포 노트 폴더가 있으면:
   - `decisions.md`, `lessons.md`는 제목(`##`)부터 훑고, 이번 작업에 걸리는 항목만 본문을 읽는다
   - `bugs.md`는 이번 작업이 건드릴 파일·모듈 이름으로 `grep` 해서 걸린 항목만 읽는다
   - `inbox.md`(`/memo`로 던진 메모)는 최근 것만 훑는다. 정리 안 된 메모라고 밝히고 인용한다
3. **꺼낼 지식** — 노트는 쌓기만 하고 꺼내지 않으면 쓸모가 없다
   - 이번 작업에 쓸 수 있는 항목만 최대 5개 고른다. 억지로 채우지 않는다
   - 노트 폴더가 없거나 비어 있으면 "레포 노트 없음"이라고 보고만 한다. 만들지 않는다

보고 형식:

- 읽은 파일 목록 (경로 그대로)
- 없어서 못 읽은 것 (`CLAUDE.md 없음`, `레포 노트 없음` 등)
- `쓸 만한 지식:` `<파일>#<항목 제목> — 이번 작업 어디에 쓰일지` 한 줄씩 (없으면 `쓸 만한 지식: 없음`)
- 노트가 실제 코드와 어긋나 보이면 `노트 어긋남:`으로 짚는다 (예: 노트는 A 라이브러리, 코드는 B)
- 읽은 내용 요약은 인터뷰에 필요한 만큼만

## 2. 인터뷰

사용자 머릿속에만 있는 맥락을 끌어낸다. 레포에서 읽을 수 있는 건 묻지 않는다.

- 질문은 한 번에 **3~5개 묶어서**. 하나씩 핑퐁하지 않는다
- 두루뭉술한 답("대충", "알아서", "좋게")은 되받아친다: 무엇을, 얼마나, 어떻게 확인할지 구체화될 때까지
- 사용자가 모르면 선택지를 2~4개 주고 추천을 하나 표시한다
- **연구·분석 작업이면 첫 묶음에서** AI 몫(스윕·정리·지표·시각화)과 사용자 몫(가설·해석·판단)을 먼저 긋는다
- 목표·제약·완료 기준·검증 방법이 다 나올 때까지 계속한다
- 인터뷰를 건너뛸지는 사용자가 정한다. 기본값은 인터뷰

## 3. CLAUDE.md (없을 때만)

- **인터뷰가 끝난 뒤에** 만든다. 인터뷰 전 생성 금지
- 내용: 스택, 폴더 구조, 실행·테스트 명령, 코드 규칙, 중요한 제약. 짧게(200줄 이하). 매 세션 통째로 읽히기 때문이다
- 만들기 전에 사용자에게 한 번 묻는다. 팀 레포면 다른 팀원도 영향을 받는다

## 4. 계획 — 플랜 모드

인터뷰가 끝나면 플랜 모드로 들어가 계획을 쓴다. 칸:

- 컨텍스트
- 참고할 노트 (1단계 3번에서 고른 것. 계획의 어느 할 일에 쓰는지까지)
- 목표
- 제약
- 할 일
- 사용자가 할 것
- 검증 기준
- 출력 형식

**인터뷰에서 나온 것만 쓴다.** 사용자가 말하지 않은 기능·규칙을 끼워 넣지 않는다. 모르는 칸은 비우지 말고 `[확인 필요]`로 적는다.

## 5. 승인 → 모드 → 실행

- 사용자가 승인하기 전에는 코드·노트를 고치지 않는다
- 승인된 계획의 목표·검증 기준은 `/check`가 서브에이전트에 넘기므로 대화에 그대로 남겨둔다
- 승인되면 실행 전에 **mode 스킬 절차로 모드를 묻는다**(모드 없음 · 절약 · 기본 · 강화 · 최대 · 극한, 추천 하나 표시). 추천은 mode 스킬의 추천 규칙을 따르고, 할 일이 서로 독립인 부분 2개 이상이면 `모드 없음`을 추천하지 않는다
  - `모드 없음`이면 메인이 이 계획대로 직접 실행한다
  - 다른 모드면 이 계획과 "참고할 노트"가 그 모드의 1단계 인터뷰 결과가 된다. 인터뷰를 다시 하지 않는다
  - 이 질문으로 모드가 정해졌으므로 이후 이 작업의 후속 메시지에는 모드를 다시 묻지 않는다
- 작업 중 결정·버그 원인·실패가 쌓이면 `/reflect`를 쓰라고 한 줄로 알려준다 (직접 쓰지는 않는다)
