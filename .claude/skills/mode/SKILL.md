# mode — 작업마다 모드는 사용자가 고른다

## 언제 묻나

- **묻는다**: 새 작업을 실행하라는 요청. 파일 수정, 명령 실행, 코드·문서·분석 결과물 만들기, 조사해서 정리하기. 작아 보여도 묻는다.
- **묻지 않는다**:
  - 순수 질문·설명·대화 (결과물을 만들지 않는 답)
  - 진행 중인 작업의 답변이나 후속 지시 (그 작업의 모드를 그대로 쓴다)
  - 사용자가 이미 모드를 정했을 때 (`/lite` 같은 슬래시 명령, "절약 모드로 해줘")
  - `/check` 요청
  - `/start` 진행 중 (start 스킬이 계획 승인 뒤 이 절차로 직접 묻는다. 그때는 인터뷰를 건너뛴다)
  - 노트 기록 명령 (`/memo`, `/reflect`)
- 애매하면 묻는다.
- 묻기 전에는 작업용 도구를 쓰지 않는다. 추천을 정하려고 요청을 읽고, 필요하면 저장소 구조를 한두 번 훑는 것까지만 한다.

## 모드 여섯 가지

절약~최대 네 모드는 구현 모델과 검증을 한 칸씩 올리고, 한도는 단계마다 약 3배씩 오른다. 극한은 그 위에서 한도 대신 품질만 보고 Fable 5.2를 쓴다. 비용은 작업 단위 3개 기준, 기본 모드 = 1 (`budget.js --compare` 결과, 추정).

| 선택지 | 스킬 | 구현 | 검증 | 비용 | 맞는 일 |
|---|---|---|---|---|---|
| 모드 없음 | — | 메인이 직접 | 메인이 직접 확인 | 작은 일이면 가장 쌈 | 몇 줄 수정, 파일 하나, 바로 확인되는 일 |
| 절약 | `lite` | Haiku max (어려운 단위 Sonnet medium) | test + 가벼운 review (Sonnet) | 약 0.37배 | 스펙이 분명한 작업 여러 개, 한도를 아낄 때 |
| 기본 | `orchestrate` | Sonnet medium (쉬운 단위 Haiku, 까다로운 단위 Opus medium) | test + review (Opus xhigh) | 1배 | 일반 기능 구현, 여러 곳 버그 수정, 연구 분업 |
| 강화 | `plus` | Opus medium (worktree) | 단위 테스트 + 통합 test + 리뷰 2 + `상` 지적 반박 검증 | 약 3배 | 남에게 보여줄 코드, 회귀가 걱정되는 수정, 중요한 증명 |
| 최대 | `super` | Opus xhigh | 설계 후보 3 + 리뷰 3 + 반박 검증 15 + 판정 | 약 8.6배 | 큰 작업, 설계가 갈리는 일, 출시 직전 |
| 극한 | `fable` | Fable high (설계 후보 3도 Fable, 증명은 Fable max) | 리뷰 Opus 3 + Fable 1 + 반박 검증 전부 + Opus 판정 | Max 기준 약 22배 (Pro는 Fable이 크레딧으로 따로 청구) | 한도보다 결과가 중요한 일. Max 이상 + `ORCHESTRATE_FABLE=1` |

Pro 기준 절대값은 단위 3개에 절약 약 1.1–1.4%, 기본 약 3–4%, 강화 약 9–12%, 최대 약 27–34%다. Max는 ÷5, Ultra는 ÷10. 극한은 Max 기준 약 15–16%(그중 Fable 약 12%, Fable은 주간 한도의 절반까지만), Ultra 약 7.5–8%다.

## 묻는 법

1. **추천을 정한다** (아래 "추천 규칙").
2. **숫자를 준비한다.** 요금제를 알면(CLAUDE.md 등) 요청을 보고 작업 단위 수 N을 어림잡아 돌린다.
   ```bash
   node .claude/scripts/budget.js --plan <요금제> --compare --units <N>
   ```
   이 레포는 플러그인이 아니라 `.claude/` 에 풀어 두었다 — 추정기는 `.claude/scripts/budget.js`. 요금제를 모르면 위 표의 상대 비용만 쓴다. 증명 작업이면 `--preset proof --compare`.
3. **1차 질문** — AskUserQuestion, header `모드`. 질문 도구는 선택지가 4개까지라 여섯 개를 두 번에 나눠 묻는다. 순서는 항상 아래와 같다(매번 같은 자리에 있어야 고르기 쉽다). 추천 선택지 라벨 끝에 `(추천)`을 붙이고, 질문 문장에 추천 이유를 한 줄 넣는다.
   - `모드 없음` — 워커 없이 메인이 직접 한다
   - `절약` — Haiku 위주 구현, 테스트 + 가벼운 리뷰 (기본의 약 3분의 1)
   - `기본` — Sonnet 구현 + 테스트·Opus 리뷰
   - `더 높은 모드` — 강화·최대·극한 중 하나를 한 번 더 묻는다
   요금제를 알면 설명에 그 요금제의 % 범위를 넣는다.
4. **2차 질문** — 1차에서 `더 높은 모드`를 골랐을 때만. header `단계`.
   - `강화` — Opus medium 구현, 단위 테스트, 리뷰 2·`상` 지적 검증 (기본의 약 3배)
   - `최대` — Opus xhigh 구현, 설계 후보 3, 리뷰 3, 반박 검증 15 (강화의 약 3배)
   - `극한` — 설계·구현을 Fable로, 리뷰 4·반박 검증 전부. 한도보다 품질 (Max 기준 최대의 약 2.5배, Pro는 크레딧 별도). `ORCHESTRATE_FABLE`이 꺼져 있으면 설명에 "켜야 쓸 수 있음"을 붙인다
5. 질문 도구가 없으면 같은 여섯 개를 번호 목록(1 모드 없음 ~ 6 극한)으로 보여주고 번호로 답해 달라고 한다.
6. 사용자가 다른 답을 직접 입력하면(예: "기본인데 리뷰는 빼") 그 뜻대로 가장 가까운 모드를 고르고, 바꾼 부분을 계획에 적는다.
7. **답을 받을 수 없으면**(예약 실행처럼 사용자가 없을 때): 모드 없음·절약·기본 중 추천으로 진행하고, 그렇게 골랐다고 맨 위에 적는다. 강화·최대·극한은 사용자 답 없이 고르지 않는다.

## 고른 뒤

- **모드 없음**: 워커 없이 메인이 직접 한다. 이 플러그인의 다른 절차는 쓰지 않는다. 작업이 생각보다 커지면 멈추고 모드를 다시 고를지 묻는다.
- **절약** → `lite`, **기본** → `orchestrate`, **강화** → `plus`, **최대** → `super`, **극한** → `fable` 스킬을 불러 그대로 따른다.
- 고른 모드는 그 작업이 끝날 때까지 유지한다. 사용자가 바꾸자고 하면 바꾼다. 메인이 판단해서 모드를 올리거나 내리지 않는다. 필요해 보이면 이유와 예상 사용량을 붙여 묻는다.

## 추천 규칙

- **모드 없음**: 파일 하나·몇 줄, 메인이 바로 확인할 수 있는 일. 워커를 띄우는 비용(지시서, 새 맥락)이 일보다 크다.
- **절약**: 바꿀 내용을 메인이 쉽게 정할 수 있는 작업 여러 개(이름 바꾸기, 정해진 수정 여러 파일, 데이터 처리). 사용자가 한도를 아끼고 싶다고 했을 때.
- **기본**: 독립 부분이 2개 이상인 일반 작업. 잘 모르겠으면 기본.
- **강화**: 품질이 중요하다고 했거나(남에게 보여줄 코드, 배포), 회귀가 걱정되는 수정, 중요한 증명.
- **최대**: 큰 작업, 설계 방향이 갈리는 일, 출시 직전 검토. 사용자가 품질을 최대로 원한다고 했을 때.
- **극한**: 사용자가 한도는 상관없다고 했거나 Fable을 쓰고 싶다고 했을 때. 메인이 먼저 추천하지 않는다(Pro에서는 실제 돈이 나간다).
- 한도를 고려한다:
  - Pro에서는 최대를 먼저 추천하지 않는다(단위 3개에 주간 한도의 약 3분의 1).
  - 남은 주간 한도를 알면, 추천 모드의 추정 상단이 남은 한도의 절반을 넘을 때 한 단계 낮춰 추천하고 이유를 적는다.
- Fable은 극한에서만 쓴다.

## 하지 말 것

- 묻기 전에 작업 시작하기 (파일 수정, 워커 띄우기, 긴 명령 실행).
- 선택지 순서 바꾸기, 여섯 개 중 일부 빼기.
- 같은 작업의 후속 메시지마다 다시 묻기.
- 사용자에게 묻지 않고 모드 바꾸기.
