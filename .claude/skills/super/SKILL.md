# super — 울트라코드 엔진 + 모델 계층

> 원본: orchestrate 플러그인 v2.2.0 의 super 스킬(사용자가 올림 2026-11-04). 이 레포에서는 `/super` 로 부른다(플러그인이 아니라 `orchestrate:` 가 안 붙는다 · 에이전트도 `su-*` 그대로). **병합 규칙은 orchestrate 스킬 머리의 '이 레포에서 바꾼 셋' 1 을 따른다** — 메인이 checker test 통과 · review 에 실패 없음이면 main 에 합치고, 실패 · 의심이 있으면 보고하고 답을 기다린다(아래 '사용자 승인 없이 기본 브랜치에 병합하기'는 그 경우를 말한다).

orchestrate와 같은 원칙(메인이 지휘, 워커가 실행, 독립 검증)을 따르되, 실행을 **동적 워크플로 스크립트**로 옮겨 규모와 교차 검증을 키운 모드다. 한도를 일반 orchestrate보다 훨씬 많이 쓴다. 대충 끝내도 되는 작업에는 쓰지 않는다.

트랙은 둘이다.
- **코드 트랙**: 기능 구현, 마이그레이션, 대규모 수정 (1~6단계)
- **증명 트랙**: 수학 증명, 물리 유도 (7단계)

## 핵심 규칙: 모델 계층은 에이전트 타입으로 고정한다

워크플로 에이전트는 따로 지정하지 않으면 **세션 모델로** 돈다. 그래서 모든 `agent()` 호출은 아래 전용 에이전트 타입을 지정한다. 모델·노력·최대 턴 수는 각 에이전트 파일 머리말에 고정돼 있다.

| 단계 | 에이전트 | model | effort | 근거 |
|---|---|---|---|---|
| 정찰 | `su-scout` | haiku | high | 사실 수집. 같은 한도로 가장 많이 돈다 |
| 설계 후보 ×3 | `su-designer` | opus | xhigh | Opus xhigh는 같은 점수대에서 Sonnet max보다 싸다 |
| 설계 판정 / 최종 판정 | `su-judge` | opus | max | 호출 수가 적은 최종 판단 |
| 구현 | `su-builder` | sonnet | high | 에이전트 코딩에서 Sonnet이 강하고 high가 효율 구간. worktree 격리가 파일에 고정 |
| 테스트 | `su-tester` | haiku | high | 기계적 확인 |
| 리뷰 ×3 관점 | `su-reviewer` | opus | xhigh | 테스트가 못 잡는 판단 |
| 중복 정리 | `su-dedupe` | haiku | high | 합치기만, 판정 안 함. Opus 검증 호출 수를 줄인다 |
| 반박 검증 | `su-verifier` | opus | high | 지적 하나씩 재현으로 판정 |
| 증명·유도 작성 | `su-prover` | opus | xhigh | 증명 트랙 |
| 증명 검증 ×3 관점 | `w-proof-verify` | opus | high | 증명 트랙. orchestrate와 공용 |
| 잡일 | `su-chore` | haiku | low | 기계적 작업 |

- 에이전트 목록에는 `orchestrate:su-builder`처럼 플러그인 이름이 붙어 보일 수 있다. 보이는 이름 그대로 쓴다.
- **에이전트 타입을 지정했으면 `model`·`effort`를 같이 넘기지 않는다.** 호출 때 넘긴 값이 파일 설정보다 우선해서 계층이 덮어써진다. (Agent 도구 호출은 플러그인 훅이 막는다. 워크플로 스크립트 안의 호출은 훅이 못 보므로 스크립트를 쓸 때 직접 지킨다.)
- 쓰지 않는 설정: Sonnet xhigh·max(같은 점수를 Opus가 더 싸게 냄), Fable(점수가 낮고 한도를 훨씬 많이 먹음).
- 스크립트에 에이전트 타입을 지정하는 정확한 문법은 `/workflow-authoring` 스킬의 참조를 따른다. 타입을 지정할 수 없으면 모델이라도 표대로 명시하고, 노력이 세션 값을 따라갔다는 사실을 보고에 적는다.

### 모델을 못 쓸 때

opus 에이전트가 실패하면(요금제·한도) 그 단계만 같은 에이전트를 `model: "inherit"`로 다시 부른다. 그래도 안 되면 그 단계를 멈추고 보고한다. sonnet·haiku 단계는 바꾸지 않는다. 낮춘 곳은 보고의 "계층에서 벗어난 곳"에 적는다.

## 0단계 — 준비와 동의

1. orchestrate 스킬의 **1단계 인터뷰를 그대로** 한다. 목표·완료 기준·범위가 확정되지 않으면 워크플로를 띄우지 않는다.
2. 환경을 확인한다.
   - `echo "$CLAUDE_CODE_EFFORT_LEVEL"`. 값이 있으면 모든 에이전트의 effort를 덮어써서 계층이 무너진다. 사용자에게 알리고, 끄고 다시 시작할지 묻는다.
   - 워크플로가 켜져 있는지(`/workflows`가 있는지). 꺼져 있으면 아래 "워크플로 없이" 방식으로 간다.
3. `/workflow-authoring` 스킬을 불러 스크립트 문법을 확인한다.
4. 사용자에게 한 번에 알리고 동의를 받는다.
   - 이 모드는 한도를 많이 쓴다. 정확한 양은 2단계에서 작은 조각으로 재서 알려준다.
   - 메인 세션은 Opus를 권장한다. `/effort ultracode`를 켜면 큰 워크플로 경고와 동시 실행 제한이 풀린다(켜지 않아도 이 스킬이 워크플로를 요청하므로 동작한다).
   - 예상 에이전트 수(아래 "규모").
5. 작업 중 에이전트가 쓸 도구를 허용 규칙에 미리 넣으라고 안내한다. 긴 실행 중간에 권한 질문이 뜨면 실행이 멈춘다.

### 규모 — 크기 가이드라인을 프롬프트로 덮어쓴다

Claude Code의 워크플로 크기 가이드라인(`workflowSizeGuideline`, Pro 기본 `small` = 5개 미만, 그 외 기본 `medium` = 10개 미만)은 상한이 아니라 **조언**이고, 규모를 명시한 요청이 있으면 그 요청이 이긴다. 그래서 워크플로를 요청할 때 "이 워크플로는 가이드라인과 관계없이 에이전트 약 N개 규모로 짠다"라고 적는다.

- 워크플로 A: 정찰(영역 수) + 설계 3 + 판정 1
- 워크플로 B1: 단위 수 × (구현 1 + 테스트 1 + 수정 최대 2회 × 2)
- 워크플로 B2: 리뷰 3 + 중복 정리 1 + 반박 검증(최대 15) + 판정 1
- 증명 트랙: 작성 1 + 검증 3, 수정 라운드마다 + 4 (최대 2라운드)
- 한 워크플로가 60개를 넘을 것 같으면 사용자에게 먼저 묻는다.
- 사용자가 `workflowSizeGuideline`을 직접 `small`로 정해 뒀으면 사용자의 선택이므로, 덮어쓰기 전에 한 번 묻는다. 기본값인지는 `/config` 행의 "default" 표시로 안다.

### 워크플로 없이

워크플로를 쓸 수 없으면 같은 단계를 **Agent 도구로** 실행한다. 이때도 위 전용 에이전트 타입을 쓰고, 독립 작업은 한 메시지에서 병렬로 띄운다. 동시 실행 서브에이전트 한도(기본 20개)를 넘지 않게 나눠서 띄운다.

## 1단계 — 워크플로 A: 정찰과 설계

워크플로는 실행 중에 사용자 입력을 받지 못한다. 그래서 사용자 승인이 필요한 지점마다 워크플로를 나눈다.

1. **정찰**: 영역마다 `su-scout`를 병렬로 띄운다. 영역은 작게 나눈다(Haiku는 프롬프트가 10만 토큰을 넘으면 5배 가격 구간이다). 결과는 파일·진입점·테스트 명령 목록을 스키마로 받는다.
2. **설계 후보**: `su-designer` 3개를 서로 다른 관점으로 병렬로 띄운다. **관점은 메인이 인터뷰 결과를 보고 고른다.** 사용자가 정한 우선순위에서 서로 부딪히는 축 셋을 고른다(예: 게임이면 재미 / 성능 / 구현 비용, 연구 도구면 정확성 / 재현성 / 사용 편의). 고르기 어려우면 단순성 / 성능·정확성 / 확장성·유지보수. 각 설계자는 정찰 결과와 인터뷰 요약만 받고 다른 후보는 보지 못한다.
3. **설계 판정**: `su-judge`가 세 후보를 비교해 최종안을 낸다. 최종안은 작업 단위 목록(파일, 목표, 명령으로 확인 가능한 완료 기준, 기준 브랜치)과 "결정 필요" 목록이다.

A가 끝나면 메인은 최종안, 후보 비교표, 결정 필요 목록을 사용자에게 보여주고 **승인을 받는다.**

## 2단계 — 작은 조각으로 비용 확인

작업 단위가 3개 이상이면 먼저 **한 단위만** 워크플로 B1으로 돌린다. `/workflows`에서 에이전트별 토큰 사용량을 보고, 전체 예상치(이 단위 × 단위 수 + 리뷰 몫)를 사용자에게 알린 뒤 나머지를 진행한다.

## 3단계 — 워크플로 B1: 구현과 단위 테스트

시작 전에 메인은 커밋 안 한 변경을 커밋하거나, 각 단위 지시서에 기준 브랜치를 적는다. `su-builder`는 worktree에서 일하고, worktree는 메인의 현재 HEAD가 아니라 기본 브랜치에서 갈라지기 때문이다.

작업 단위마다(서로 독립이면 병렬로):

1. **구현**: `su-builder`가 단위 하나를 구현하고 커밋한다.
2. **테스트**: `su-tester`가 그 단위의 완료 기준을 실행한다.
3. **수정 루프**: 실패하면 실패 표와 재현 명령만 `su-builder`에게 다시 준다. **최대 2번.** 같은 실패가 반복되면 지시서 문제일 가능성이 높으니 그 단위는 멈추고 실패로 기록한다.

B1은 단위별 결과(브랜치, 커밋, 테스트 표, 실패 단위)를 돌려준다.

## 4단계 — 병합과 통합 테스트

1. 메인이 통과한 단위의 브랜치를 작업 브랜치로 합친다. 저장소 규약을 따르고, 기본 브랜치에는 합치지 않는다. 충돌이 나면 메인이 몇 줄 수준에서만 풀고, 그 이상이면 멈추고 보고한다.
2. 합친 상태에서 이 플러그인의 **check 스킬 test 모드**(`checker-test`)를 돌린다. 단위별로 통과했어도 합치면서 깨질 수 있다. 실패하면 원인 단위의 `su-builder`에게 실패 표를 넘겨 고치게 한다(최대 2번).

## 5단계 — 워크플로 B2: 병합된 결과 리뷰와 반박 검증

리뷰는 **병합된 diff**(`git diff <기준 브랜치>...HEAD`)로 한다. 단위별 diff만 보면 합치면서 생긴 문제를 놓친다.

시작 전에 check 스킬 1단계의 시작 상태 기록(스냅샷)을 한다. 리뷰어와 검증자는 명령을 실행하며 흔적을 남길 수 있다.

1. **다관점 리뷰**: `su-reviewer` 3개를 서로 다른 관점으로 병렬로 띄운다. 기본 관점은 스펙·완료 기준 일치 / 정확성·경계 조건 / 회귀·보안. 리뷰어는 목표·완료 기준·병합된 diff·레포 경로만 받는다. 구현자의 설명은 넘기지 않는다. 지적마다 심각도(상/중/하)를 단다.
2. **중복 정리**: `su-dedupe`가 세 리뷰어의 지적을 합치고 심각도 순으로 정렬한다.
3. **반박 검증**: 정렬된 목록의 **상위 15개**에 대해 지적마다 `su-verifier`를 띄운다. `성립`만 남기고, `미확인`은 따로 표시하고, `기각`은 근거와 함께 버린다. 16번째부터는 "검증 안 함"으로 표시해 그대로 넘긴다.
4. **최종 판정**: `su-judge`가 성립한 지적을 심각도 순으로 정리한다.

B2가 끝나면 check 스킬 4단계(흔적 정리)를 한다. 리뷰·검증 에이전트가 만든 새 파일만 지우고, 추적 파일이 바뀌었으면 되돌리지 말고 보고한다.

## 6단계 — 보고 → 사용자가 결정

orchestrate 5단계 양식에 아래를 더한다.

```
## 설계
- 고른 관점 3개와 이유, 후보 비교표, 최종안, 사용자가 정한 항목
## 검증
- 단위별 테스트 표, 병합 후 통합 테스트 표
- 성립한 리뷰 지적 (심각도 순, 그대로)
- 미확인 / 검증 안 함 / 기각 지적 수
- 리뷰·검증 에이전트가 만들고 지운 파일
## 비용
- 워크플로별 에이전트 수와 토큰 사용량 (/workflows 기준)
- 계층에서 벗어난 곳 (에이전트 타입을 못 쓴 단계, inherit로 낮춘 단계)
```

마지막에 묻는다: "고칠까? 고친다면 어느 항목부터?" 리뷰 지적은 사용자 답 전에 고치지 않는다.

같은 종류의 작업을 반복할 거면 `/workflows`에서 실행을 골라 `s`로 저장하라고 알려준다. 저장한 스크립트를 이 플러그인의 `workflows/` 폴더에 넣으면 `/orchestrate:<이름>`으로 다른 프로젝트에서도 쓸 수 있다.

## 7단계 — 증명 트랙

수학 증명이나 물리 유도에 쓴다. 저장소가 없어도 된다. 인터뷰에서 확정할 것: 증명할 명제(또는 구할 식), 쓸 수 있는 가정·근사, 결과 형식.

워크플로 P (라운드 최대 3번: 처음 1 + 수정 2):

1. **작성**: `su-prover`가 증명·유도를 쓴다. 반례를 찾으면 증명 대신 반례를 돌려주고, 그 경우 검증은 반례 하나만 확인한다.
2. **독립 검증**: `w-proof-verify` 3개를 서로 다른 관점으로 병렬로 띄운다.
   - 논리: 단계마다 앞 단계와 근거에서 실제로 따라 나오는가
   - 정의·경계: 정의가 중간에 바뀌지 않는가, 빈 경우·극한·특수값·차원이 맞는가
   - 반례: 결론을 깨는 입력·상황을 적극적으로 찾고 수치로 확인한다
   검증자는 **증명문만** 받는다. 작성자의 설명, 확신 표현, 다른 검증자 결과는 넘기지 않는다.
3. **판정 합치기**(스크립트가 한다): 단계마다
   - 누구든 구체적 반례나 계산 결과로 `틀림`을 냈으면 → 틀림
   - 아니면 2명 이상 `성립` → 성립
   - 나머지 → 근거 부족
4. 틀림·근거 부족 단계가 있으면 그 단계 번호와 판정 이유만 `su-prover`에게 주고 다시 쓰게 한 뒤 2~3을 반복한다. 검증자는 매 라운드 새로 띄운다.

보고: 최종 증명(LaTeX), 단계별 판정 표(검증자 3명 각각 + 합친 결과), 남은 쟁점. 검증자끼리 끝까지 갈리는 단계는 메인이 고치려 하지 말고 쟁점을 정리해 사용자에게 넘긴다.

## 하지 말 것

- 인터뷰와 사용자 동의 없이 워크플로 띄우기.
- 에이전트 타입 없이, 또는 타입과 함께 `model`·`effort`를 넘겨 `agent()` 호출하기.
- 설계와 구현을 한 워크플로로 묶어 사용자 승인 단계를 건너뛰기.
- 병합 전 diff만 리뷰하고 끝내기.
- 상한 없는 수정·탐색 루프.
- 반박 검증을 거치지 않은 리뷰 지적을 확정된 문제로 보고하기.
- 증명 검증자에게 작성자의 설명이나 다른 검증자 결과 넘기기.
- 사용자 승인 없이 기본 브랜치에 병합하기.
