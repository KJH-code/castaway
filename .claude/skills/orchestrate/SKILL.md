# Orchestrate — 기본 모드: 메인이 지휘하고 워커가 일한다

모드는 여섯 가지 중 사용자가 고른다(`mode` 스킬): 모드 없음 · 절약(`lite`) · **기본(이 스킬)** · 강화(`plus`) · 최대(`super`) · 극한(`fable`). 절약과 강화는 이 스킬의 절차를 따르면서 정해진 부분만 바꾼다.

> 원본: orchestrate 플러그인(Jaehyeok Kim · 사용자가 올림) — v2.0.0(2026-10-30) → 11-02 판 → v2.2.0(2026-11-04) → **v3.3.0**(2026-11-10 · 모드 여섯(모드 없음 · 절약 `lite` · 기본 · 강화 `plus` · 최대 `super` · 극한 `fable`)을 새 작업마다 묻는 `mode` 스킬과 훅 `ask-mode.js` · 한도 추정기 `.claude/scripts/budget.js` · 에이전트 `checker-lite` · `w-implement-lite` · `w-implement-opus` · `*-fable`). 이 레포는 플러그인이 아니라 `.claude/` 아래에 풀어 두었다 — 에이전트 이름에 `orchestrate:` 가 안 붙고, 모드 스킬은 `/lite` · `/plus` · `/super` · `/fable` · `/mode`, 훅은 `.claude/settings.json` 이 `.claude/hooks/` 의 둘을 부른다. **이 레포에서 바꾼 셋(사용자 결정)**:
> 1. **병합은 메인(Opus)이 한다** — CLAUDE.md '작업 흐름'대로 늘 main 에 합친다(checker test 통과 · review 에 '실패' 없음이면). review 에 실패·의심이 있으면 그대로 보고하고 사용자 답을 기다린다. 워커 · checker 는 푸시 · PR · 병합을 안 한다. 모든 모드(절약 · 강화 · 최대 · 극한)에 같다.
> 2. 구현 위임 · 인터뷰는 이 스킬 그대로.
> 3. 비용(메인이 정함) — general-purpose 를 띄우는 고정 비용이 **5.8만 토큰**이다(2026-10-30 잰 값 · haiku · 한 줄 답). 그래서 워커 · 검수는 이 레포 에이전트(`.claude/agents/` · 일하는 것들은 끝에 '이 레포(CASTAWAY)에서' 절)로 띄우고, general-purpose 는 그것이 안 잡힐 때만 쓴다(에이전트 파일을 막 만든 세션 — 그때만 `model` · `effort` 를 표대로). 읽기만 하는 조사는 `Explore` + model(CLAUDE.md 를 안 읽는다).

## 구조

사용자 ↔ **메인(너, 고노력)** → 워커 서브에이전트들(작업 성격에 따라 모델·노력 차등) → 메인이 검수 → 사용자에게 보고 → **결정은 사용자가 한다.**

메인의 일은 판단이다. 실행은 워커에게 넘긴다. 이득은 두 가지다.
- **컨텍스트 보호**: 워커가 파일 수십 개를 뒤져도 메인에는 결론만 들어온다. 메인은 대화가 길어져도 흐려지지 않는다.
- **한도·속도**: 스펙이 확정된 반복 작업은 한도를 덜 먹는 워커가 하고, 독립 작업은 병렬로 돈다.

품질은 나눈다고 오르지 않는다. **품질은 메인이 쓰는 지시서의 질로 정해진다.** 저노력 워커는 지시서에 없는 것을 채우지 않는다.

작업 도중에 다른 모드가 맞아 보이면(생각보다 크거나 작으면) 이유와 예상 사용량(`budget.js --compare`)을 붙여 사용자에게 묻는다. 사용자가 고르기 전에는 모드를 바꾸지 않는다.

## 시작할 때 확인

- 메인 세션은 `/model`을 Opus로, `/effort`를 xhigh로(최소 high) 사용자가 직접 맞춘다. 이 스킬은 메인의 모델·노력을 바꿀 수 없다. 이미 맞춰져 있으면 생략.
  - xhigh인 이유: Opus 5.5는 high→xhigh에서 추론 평가가 크게 오르고(HLE +8, CritPt +8, Terminal-Bench-Science +13점) xhigh→max는 거의 안 오른다. 지시서의 질이 전체 품질을 정하므로 메인은 꺾이는 점에 둔다.
  - 메인을 Fable로 두지 않는다. Fable은 API 환산 금액당 한도를 Opus보다 약 2.4배 빨리 쓰고, 주간 한도의 절반까지만 쓸 수 있다.
- `echo "$CLAUDE_CODE_EFFORT_LEVEL"`를 실행한다. 값이 있으면 이 환경변수가 모든 에이전트의 effort 설정보다 우선해서 계층이 무너진다. 사용자에게 알리고, 끄고 다시 시작할지 묻는다.
- **요금제**(Pro / Max / Ultra)를 안다. CLAUDE.md에 `요금제: Max` 같은 줄이 있으면 묻지 않는다. 없으면 2단계 계획과 함께 한 번 묻고, 답이 없으면 Pro로 가정한다(가장 보수적). 요금제는 한도 추정과 Fable 사용 여부를 정한다.

## 1단계 — 인터뷰

바로 만들지 않는다. 먼저 묻는다. 사용자가 이미 다른 인터뷰·계획 스킬을 쓰고 있으면 그걸 따른다.

**`/start`를 거쳐 왔으면** 그 승인된 계획이 인터뷰 결과다. 인터뷰를 다시 하지 않는다. 계획의 **"참고할 노트"** 목록을 그대로 가져가 지시서에 쓴다. 3번 요약 대신 계획을 원본으로 삼는다.

**레포 노트(`docs/notes/`, CLAUDE.md의 `notes:` 줄이 있으면 그 경로)가 있으면** — 이유: 노트 지식이 메인 머릿속에만 있으면 워커는 같은 함정을 또 밟는다
- `/start` 없이 바로 왔으면 `decisions.md`·`lessons.md` 제목을 훑고, `bugs.md`를 건드릴 파일 이름으로 검색해서 이 작업에 맞는 항목을 최대 5개 골라 실제로 읽는다. 고른 목록을 3번 요약에 한 줄로 넣는다.
- 노트 폴더가 없으면 이 단락은 건너뛴다.

1. 저장소의 CLAUDE.md, README, 브랜치·커밋 규약을 먼저 읽는다. 이 레포는 그 계통 노트(`docs/notes/` — CLAUDE.md '계통별 노트' 표)에서 고칠 이름을 grep 해 그 대목도 읽는다. 읽어서 알 수 있는 건 묻지 않는다.
2. 아래가 확정될 때까지 집요하게 묻는다. 한 번에 2~4개씩, 답이 애매하면 다시 묻는다.
   - **목표**: 끝나면 무엇이 존재하는가
   - **완료 기준**: 명령이나 화면으로 확인 가능한 조건 ("잘 동작"은 기준이 아니다)
   - **범위**: 건드리면 안 되는 것
   - **우선순위**: 시간이나 한도가 모자라면 뭘 버리나
   - **품질 수준**: 대충 돌아가면 되나, 남한테 보여줄 건가
3. 확정된 내용을 5~10줄로 요약해 보여주고 확인받는다. 이 요약이 이후 모든 지시서의 원본이다.

## 2단계 — 쪼개기

- **나눈다**: 서로 독립적인 일. 다른 파일·다른 영역(서버 / 클라이언트 / UI처럼 **영역별**로 나누는 게 코딩에선 가장 좋다 — 건드리는 파일이 안 겹쳐서 충돌이 적다), 자료 여러 개 따로 조사, 데이터셋 여러 개 따로 처리.
- **나누지 않는다**: 한 단계 결과가 다음 단계를 바꾸는 일. 연구 설계, 원인 모를 디버깅, 결과 해석. 메인이 직접 쥔다.
- **너무 잘게 쪼개지 않는다.** 새 워커는 매번 저장소를 처음부터 읽어 맥락을 쌓고, 그게 한도를 쓴다(Claude 한도는 이미 쌓인 맥락을 다시 읽는 캐시 읽기는 아주 가볍게 세지만, 새로 쌓는 건 그렇지 않다). 같은 파일 묶음을 건드리는 작은 일들은 한 워커에게 묶는다.
- 의존 관계가 있으면 순서를 정한다. 독립인 것만 병렬로 띄운다.
- 쪼갠 계획(워커 목록, 순서, 각자 범위, 워커별 에이전트)과 **예상 한도 사용량**을 사용자에게 보여주고 진행한다.

### 한도 추정

```bash
node .claude/scripts/budget.js --plan <pro|max|ultra> --calls "w-implement:2,w-implement-lite:1,checker-test:1,checker:1"
```

- 이 레포는 플러그인이 아니라 `.claude/` 에 풀어 두었다(추정기 `.claude/scripts/budget.js`). 에이전트의 모델·노력은 스크립트가 agents/ 파일에서 직접 읽는다.
- 결과는 "주간 한도의 몇 %"를 범위로 준다. 제3자 측정·추정 기반이라 대략값이다. 근거·한계·줄이는 순서는 `references/budget.md`.
- 예상치 상단이 주간 한도의 20%를 넘거나, 사용자가 알려준 남은 한도의 절반을 넘으면(`--remaining`) 진행 전에 묻는다.

## 3단계 — 워커 배정

워커는 **Agent 도구**로 띄우고, `subagent_type`에 아래 **워커 에이전트**를 지정한다. 기준은 **"판단이 필요하냐, 스펙이 확정됐냐"**, 그리고 구현이면 **"그 단위가 얼마나 까다롭냐"**다.

모델·노력은 각 에이전트 파일 머리말에 고정돼 있다. **호출할 때 `model`·`effort`를 넘기지 않는다.** 호출 때 넘긴 값이 파일 설정보다 우선해서 계층이 덮어써지기 때문이다(플러그인 훅이 이런 호출을 막는다).

| 워커 | 에이전트 | 하는 일 | model | effort |
|---|---|---|---|---|
| 설계 | `w-design` | 시스템·캐릭터 설계, 판단이 필요한 하위 문제 | opus | xhigh |
| 증명 작성 | `w-proof-write` | 수학 증명, 불변량 논증 | opus | xhigh |
| 증명 검증 | `w-proof-verify` | 작성자와 **다른** 워커가 증명문만 받아 검사 | opus | xhigh |
| 구현 (기본) | `w-implement` | 스펙이 확정된 기능 구현. 이 모드의 기본 구현 워커 | sonnet | medium |
| 구현 (쉬운 단위) | `w-implement-lite` | 지시서가 파일·함수·바꿀 내용까지 정한 작은 단위 | haiku | max |
| 구현 (까다로운 단위) | `w-implement-opus` | 테스트가 얇거나 경계 처리가 까다로운 단위 | opus | medium |
| 데이터 처리 | `w-data` | 정해진 처리·분석 스크립트 실행 | haiku | max |
| 실험 실행 | `w-experiment` | 정해진 실험을 돌리고 결과 수집 | haiku | max |
| 잡일 | `w-chore` | 파일 정리, 포맷 변환, 이름 바꾸기 | haiku | medium |

배정 근거는 README "설계 근거". 짧게:
- **구현 기본은 Sonnet medium.** 실제 Claude Code 코딩 테스트에서 Opus medium과 통과율이 비슷하고(20회 중 11 vs 13) API 비용은 약 4분의 1, 구독 한도로 바꾸면 약 3분의 1이었다. Sonnet은 medium만 쓴다. high는 비용만 늘고 통과가 늘지 않았고, max는 Opus max보다 비쌌다.
- **Opus low는 쓰지 않는다.** 에이전트 코딩에서 무너진다(FrontierCode 15.8%, Terminal-Bench 31.3%).
- **Haiku는 xhigh 이상.** max도 과제당 Pro 주간 한도의 0.16%다.

### 구현 워커 고르기

단위마다 고른다. 기본은 `w-implement`(Sonnet medium).
- **쉬운 단위 → `w-implement-lite`(Haiku max).** 아래를 **모두** 만족할 때만: 지시서에 바꿀 파일·함수·내용이 다 적혀 있다 / 파일 1~3개, 의존성 설치·환경 설정·긴 셸 작업이 없다 / 기존 코드 구조를 새로 파악할 필요가 없다. Haiku는 정해진 수정은 잘하지만(FrontierCode 2.0 34.9%) 낯선 저장소 이해(SWE-Atlas-QnA 34%, Sonnet 64%)와 터미널 작업(Terminal-Bench 31%, Sonnet 66%)에 약하다.
- **까다로운 단위 → `w-implement-opus`(Opus medium).** 테스트가 얇아 경계 조건을 사람이 챙겨야 하거나, 동시성·상태 관리·보안처럼 놓치면 큰 일이 나는 단위. 같은 코딩 테스트에서 Opus가 Sonnet보다 나은 점은 경계 조건 처리였다.
- 까다로운 단위가 절반을 넘으면 강화 모드로 바꿀지 사용자에게 묻는다.
- 실험이 의존성 설치·GPU 설정·긴 셸 작업을 요구하면 `w-experiment` 대신 `w-implement`에게 맡긴다.

### 공통 규칙

- 이 레포에서는 `.claude/agents/` 에 풀어 두어 에이전트 이름 앞에 플러그인 이름이 안 붙는다(`w-implement` 그대로).
- 워커 에이전트가 목록에 없으면(플러그인 로드 실패) general-purpose로 띄우되, 그때만 `model`·`effort`를 표대로 넘기고 해당 에이전트 파일 본문을 프롬프트 맨 앞에 붙인다. 이렇게 했다는 사실을 보고에 적는다.
- 워커 지시서 공통 양식: `references/spec-template.md`. 모든 칸을 채운다. 특히 **입력**에 읽을 파일을 정확히 적는다. 워커가 뒤지는 만큼 한도를 쓴다. 워커별 역할 설명은 각 에이전트 파일에 들어 있어서 따로 붙이지 않는다.

코드 검증은 워커가 아니라 **checker 에이전트**가 한다 (4단계).

### 하위 세션 (사용자가 원할 때만)

기본은 서브에이전트다. 사용자가 "이건 하위 세션으로"처럼 **직접 들여다보고 말을 걸고 싶은 트랙**을 지정했을 때만 하위 세션으로 띄운다.

- **하위 세션** = Agent 도구에 `isolation: "remote"`. 사이드바에 메인 밑으로 붙어서 사용자가 열어 보고 직접 말을 걸 수 있다. 무겁다(새 클라우드 환경, 저장소를 새로 받음, 뜨는 데 시간 걸림).
- `subagent_type`은 서브에이전트와 **같은 워커 에이전트**를 쓴다. `model`·`effort`는 넘기지 않는다(훅이 막는다). 원격 세션이 에이전트 파일의 모델·노력을 그대로 따르는지는 확인되지 않았다. 첫 보고에 "하위 세션: 계층 미확인"을 적고, 사용자가 사이드바에서 모델을 확인해 주면 그 결과를 적는다.
- checker는 push 안 한 diff를 봐야 해서 하위 세션으로 못 간다.

1. **먼저 push.** 하위 세션은 GitHub에서 저장소를 새로 받는다. 기준 브랜치에 커밋 안 했거나 push 안 한 변경이 있으면 못 본다. 띄우기 전에 커밋·push 하고, 지시서에 기준 브랜치 이름을 적는다.
2. **이름.** Agent의 `description`을 사이드바에서 알아볼 수 있게 `<프로젝트> <트랙ID> <영역> — <할 일>`로 쓴다 (예: `Tetrafall A3 서버 — 넉백 판정`). 트랙ID는 기존 하위 세션과 겹치지 않게 이어 붙인다.
3. **호출.** 하위 세션은 항상 백그라운드로 돈다. 끝나면 알림이 온다. 기다리는 동안 메인은 다른 일을 하거나 사용자와 대화한다. 알림이 오기 전에 결과를 지어내지 않는다.
4. **동시 개수.** 하위 세션은 사용자의 사용 한도를 같이 쓴다. 동시에 **3개까지**만.
5. **결과 회수.** 하위 세션은 끝날 때 작업 브랜치를 push하고 브랜치 이름을 보고한다(지시서 보고 형식에 넣는다). 메인은 그 브랜치를 fetch해서 작업 브랜치에 합친 뒤 4단계 검수로 간다.
6. **사용자가 하위 세션에 직접 말한 것.** 하위 세션 보고에 "사용자 직접 지시" 항목을 따로 적게 하고, 메인은 그걸 원래 지시서보다 우선한다.
7. **질문이 생기면.** 하위 세션은 추측하지 않고 질문을 보고하고 멈춘다. 메인이 답할 수 있으면 SendMessage로 이어서 시키고, 판단이 필요하면 사용자에게 묻는다.

### 다시 시킬 때는 같은 워커를 이어서

수정 요청은 새 워커를 띄우지 말고 **SendMessage로 원래 워커를 이어서** 부른다. 워커는 이미 읽은 파일과 한 일을 기억하고 있어서 다시 탐색하지 않고, 남은 맥락은 캐시 읽기라 한도를 적게 쓴다. 이어 부를 수 없으면(워커가 끝나 ID가 없는 경우 등) 새로 띄우되 이전 보고(바꾼 파일·커밋)를 지시서에 붙인다.

검증 쪽(checker, 증명 검증)은 반대다. 독립성이 목적이라 **항상 새로** 띄운다.

### Fable

Fable 5.2는 극한 모드(`fable` 스킬)에서만 쓴다. 절약·기본·강화·최대에서는 쓰지 않는다. Fable이 필요해 보이면 극한 모드로 바꿀지 사용자에게 묻는다.

### 한도에 걸렸을 때

- 5시간·주간 한도는 모든 모델이 같이 쓴다. 한도 때문에 실패하면 **다른 모델로 바꿔 다시 부르지 않는다**(소용없다). 멈추고, 끝난 것·남은 것을 보고하고, 리셋 시각은 사용자가 `/usage`로 확인하게 한다.
- 사용자가 아끼고 싶다고 하면 모델 계층을 깨지 말고 규모를 줄인다(`references/budget.md` "줄이는 순서").
- 조직 정책 등으로 Opus 자체를 못 쓰는 환경이면, 같은 에이전트를 `model: "inherit"`(메인과 같은 모델)로 다시 부른다. 이때만 `model`을 넘긴다(훅도 `inherit`은 허용한다). 메인이 Fable이면 `inherit`을 쓰지 않는다(Fable 몫을 먹는다). haiku·sonnet 워커는 그대로 둔다. 낮췄다는 사실을 보고에 적는다.

### 코딩 워커를 병렬로 띄울 때
- 같은 저장소를 동시에 고치는 워커는 `isolation: "worktree"`로 띄운다.
- worktree는 기본 브랜치에서 갈라진다(메인의 현재 HEAD가 아니다). 메인이 커밋 안 한 변경이 있으면 먼저 커밋하거나, 지시서에 기준 브랜치를 명시한다.
- 합치는 건 메인이 한다. 저장소 규약을 따른다(이 레포: CLAUDE.md '작업 흐름' — 커밋 · 푸시 → PR → 곧바로 merge 커밋 · 합치기 전 `check-syntax` · `smoke`).

### 증명은 반드시 두 명
1. 증명 작성 워커(`w-proof-write`)가 쓴다.
2. 메인은 **증명문만** 증명 검증 워커에게 넘긴다. 작성자의 사고 과정·확신 표현은 넘기지 않는다. 같은 구멍을 같이 못 보게 하려는 것이다.
3. 검증 워커는 각 단계를 "성립 / 틀림 / 근거 부족"으로 판정한다.
4. 둘이 갈리면 메인이 고치려 들지 말고 쟁점을 정리해 사용자에게 보고한다.

## 4단계 — 검수

워커 결과를 그대로 믿지 않는다. 저노력 워커는 틀린 걸 자신 있게 들고 온다.

### 코드 → checker
코드 검증은 이 플러그인의 **check 스킬 절차 그대로** checker 에이전트에게 맡긴다. 메인이 자기 눈으로 "돌아가네" 하고 넘기지 않는다. 짠 쪽이 검증하면 자기 채점이 된다.

1. 워커 브랜치를 합친 작업 브랜치에서 check 스킬의 1단계(시작 상태 기록)를 한다
2. checker에게는 **워커 지시서의 목표·완료 기준 원문 + git diff + 레포 경로**만 넘긴다. 메인의 가설·대화는 넘기지 않는다
3. **test 모드** (`checker-test`: haiku, xhigh): 빌드·테스트·실행 결과를 명령 출력으로 확인
   - `실패`면 실패 표와 재현 명령을 원래 워커에게 넘겨 다시 시킨다(이어서 부른다, **최대 2번**). 같은 실패가 반복되면 지시서 문제일 가능성이 높으니 지시서부터 고친다. 2번 넘으면 멈추고 보고
   - `환경 문제`는 워커에게 돌려보내지 않는다. 코드 실패가 아니라서 워커가 고칠 수 없다. 메인이 에러 줄을 보고 명령을 고쳐 test를 다시 돌리거나, 설치·권한이 필요하면 사용자에게 묻는다
4. test 통과하면 **review 모드** (`checker`: opus, xhigh): 완료 기준 판정 + 테스트가 못 잡는 버그·스펙 어긋남
   - review 결과는 고치지 않고 **그대로** 사용자에게 보고한다. 메인이 요약하거나 걸러내지 않는다
5. check 스킬의 4단계(checker 흔적 정리)를 한다

### 코드 외
- 데이터·실험: 수치를 표본으로 다시 계산해 본다. 이상치·빈 결과·단위를 확인한다.
- 증명: 검증 워커 판정을 본다.
- 실패하면 원인을 적어 같은 워커에게(이어서) **최대 2번** 다시 시킨다. 그래도 안 되면 멈추고 보고한다.

## 5단계 — 보고 → 사용자가 결정

```
## 결과
- 무엇이 됐는지 (검수 통과한 것만)
## checker 결과
- test 표, review 표를 그대로. checker가 만들고 지운 파일 목록
## 확인 방법
- 사용자가 직접 볼 수 있는 방법 (실행 명령, 파일 위치)
## 결정할 것
- 선택지와 트레이드오프, 메인의 추천과 이유
## 안 된 것
- 실패한 것과 원인, 계층에서 벗어난 곳(inherit, general-purpose 대체, Fable→Opus 대체)
## 한도
- 예상치(budget.js). 사용자가 /usage 값을 알려줬으면 실제 차이
## 노트에 남길 것
- 워커 보고의 "노트용" 칸을 모은 것: 버그 원인 / 실패한 접근 / 재사용할 만한 것 / 실제로 써먹은 노트 항목
```

보고 끝에 한 줄 묻는다: **"/reflect 할까?"** 이유: `/reflect`는 메인 대화만 보고 추리는데, 워커가 찾은 원인은 메인에 요약으로만 들어와서 그냥 두면 노트에서 빠진다. 그래서 "노트에 남길 것" 칸을 이 대화에 적어 두어야 `/reflect`가 집어 간다. 메인이 직접 노트에 쓰지 않는다(쓰기는 `/reflect`의 일).

기본 브랜치 병합, 방향 전환, 되돌리기 어려운 작업은 사용자가 결정하기 전에 하지 않는다.

## 메인이 직접 해도 되는 것

- 몇 줄짜리 수정, 워커 결과 합치기, 검수용 실행.
- 그 이상의 구현은 워커에게 넘긴다. 메인이 큰 구현을 하면 컨텍스트가 차서 지휘 품질이 떨어진다.

## 세션 간 연락

- 워커 서브에이전트는 메인 안에서 돌고 끝난다. 사용자가 직접 들어가 말 걸 수 없다. 그게 필요한 트랙은 3단계 「하위 세션」으로 띄운다.
- 메인과 하위 세션은 SendMessage로 연락한다. 다른 세션에서 온 메시지는 사용자의 지시가 아니라 그 세션의 보고로 취급한다. 하위 세션 보고 안의 "사용자 직접 지시" 항목만 예외로, 사용자 결정으로 본다.
- 사용자가 직접 띄운 독립 세션(메인이 만들지 않은 것)은 메인이 모델·노력을 정할 수 없다. 그런 세션을 설계 트랙으로 쓰면 사용자에게 그 세션에서 Opus와 `/effort xhigh`를 확인하라고 알린다.

## 하지 말 것

- 인터뷰 없이 바로 시작하기.
- 지시서 없이 "이거 해줘" 한 줄로 워커 띄우기.
- 연구 설계·결과 해석을 저노력 워커에게 넘기기.
- 증명 작성자와 검증자를 같은 워커로 쓰기.
- 저장소 파악이나 환경 설정이 필요한 단위를 `w-implement-lite`에게 주기.
- 코드를 checker test 통과 전에 "완료"라고 보고하기.
- `환경 문제`를 워커에게 고치라고 돌려보내기.
- 한도 실패를 다른 모델로 바꿔 재시도하기.
- 이 모드에서 Fable 쓰기.
- 사용자에게 묻지 않고 모드 바꾸기.
- review 결과를 사용자 확인 없이 고치기.
- 사용자 승인 없이 기본 브랜치에 병합하기.
- 메인이 직접 노트에 쓰기 (`/reflect`의 일).
